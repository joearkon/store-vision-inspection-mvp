## 5. 测试中发现并修复的问题

### P0/P1 闭环阻断

1. **Dashboard 永久转圈**
   - 原因：Vite 从非标准目录启动时未加载代理配置，`/api/*` 返回了前端 HTML。
   - 修复：开发环境显式连接 `127.0.0.1:8797`；非 JSON 响应显示明确错误，不再无限等待。

2. **API 与 Worker 使用两套 SQLite**
   - 原因：`.env` 的 `./data` 按进程启动目录解析。
   - 修复：所有相对数据路径固定从项目根目录解析，并新增回归测试。

3. **逐帧模型调用慢且容易超时**
   - 原因：Seed 2.1 Lite 默认使用高推理强度，而门状态观察只是四分类任务。
   - 修复：显式设置 `thinking: disabled`；超时提高到 90 秒；网络/读取超时最多重试 3 次。
   - 效果：从约 1 分钟仅处理 3–5 帧，提升为约 2 分 17 秒处理完整 50 帧。

4. **事件最后出现时间错误**
   - 原因：未恢复事件把“最高置信度帧”误当作“最后仍开启帧”。
   - 修复：聚合候选新增 `last_open`，最终事件正确记录 49 秒。

5. **事件详情页空白崩溃**
   - 原因：Promise 返回给 React `useEffect`，严格模式清理阶段触发异常。
   - 修复：Effect 内调用加载函数但不返回 Promise；加入静态回归保护。

6. **证据图可能走错前端同源地址**
   - 原因：图片仍使用 `/api/media/...`，会受错误的 Vite 启动方式影响。
   - 修复：证据 URL 与 JSON API 共用明确的本地后端基址。

## 7. 尚未覆盖与风险

1. 当前 50 秒生成视频是持续开门正样本，没有真实“关闭 → 开启超过 30 秒 → 关闭”完整动作，因此本轮没有验证 `recovered_offset`。
2. 尚未跑“开启不足 30 秒”的负样本，不能仅凭本轮宣布误报率达标。
3. 合成视频可验证工程闭环，但不能替代真实门店录像的准确率验收。
4. 本轮刻意关闭飞书推送；飞书真实卡片仍需在独立测试群做一次受控验收。
5. 当前 1 fps 逐帧方案成本与延迟仍偏高。

## 8. 下一步技术方案

采用两层视频理解：

1. 首先使用火山原生 `video_url`/`file_id` 整段理解，输出疑似开门时间段；
2. 仅对疑似段的起点、28–32 秒阈值窗口和恢复点做局部高精度复核；
3. 最终 E1 仍由后端确定性规则计算，不允许模型直接生成严重度或事件结论；
4. 保留起点、确认点、峰值、恢复点证据，并记录有效覆盖率；覆盖不足则明确失败，不能判为无异常；
5. 将当前 1 fps 全量逐帧结果作为新方案的准确性基线。

该改造方向能显著减少请求次数，但必须在同一组正/负/恢复样本上与当前基线对照后才能替换默认路径。
