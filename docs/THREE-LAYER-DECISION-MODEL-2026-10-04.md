# 门店视觉巡检 MVP：语义、策略、行动三层业务定义与现状差距

> 版本：讨论稿 v0.1｜日期：2026-10-04  
> 范围：先以本项目 E1、A1、B1 的现有合成视频流程为试点；跨项目复用仅定义原则，不表示已与加盟商运营系统集成。  
> 本文是业务与实施契约，**不是新增功能的完成声明**。现有页面和代码事实以文末依据为准；凡标为“拟补”的字段、交互和验收点均未实现。

> 后续增量实施与待业务裁定项见 [视频分析判定链：字段级业务字典](DECISION-TRACE-BUSINESS-DICTIONARY-2026-10-04.md)。本文保留 2026-10-04 当时的差距记录，不将历史描述默认为当前代码状态。

## 1. 为什么做三层，而不是再做一个页面

目前已经有分析任务、规则能力、事件证据、整改跟踪、工单视图和人工操作时间线。需要解决的不是“有没有这些页面”，而是同一条结论跨页面是否保持相同含义，能否回答：**看见了什么、按哪条规则形成事件、由谁决定做什么、结果如何**。三层是现有链路的共同语言：

```text
视频/抽帧 → 视觉观察（语义层） → 规则聚合与处置建议（策略层）
         → 事件/人工确认/整改/复核（行动层） → 结果反馈
```

模型观察、规则判定、人工决定必须分开保存和展示。不能把“模型看见疑似烟雾”“后端形成 B1 事件”“管理员确认并整改”写成同一个“AI 已判定完成”。

## 2. 共同业务词典（语义层）

| 对象/术语 | 本项目定义 | 与其他对象的边界 | 当前承载 |
| --- | --- | --- | --- |
| 门店、视频源 | 业务归属和拍摄位置；演示视频源不等于物理摄像头在线 | 门店 ID/摄像头 ID 是关联键，不是模型推断 | `stores`、`camera_sources`；线上演示允许新增虚拟视频源 |
| 视频素材 | 一段上传或预置素材，记录来源、文件哈希和时长 | 合成视频、受控实拍、真实门店视频必须分别标注；不得混算识别准确率 | `video_assets` 的 `source_kind`、`sha256` 等；现阶段可复核素材为合成视频 |
| 分析任务 | 对一段视频、一个规则、一次模式的实际运行 | 一条视频可多次运行；任务完成不等于有异常或事件已处理 | `analysis_runs`，含状态、模式、规则、耗时相关时间戳、请求数、Token、模型 ID |
| 帧观察 | 模型在时间点/区域看到的可见事实、状态和证据 | 单帧命中不是业务事件；`unknown`/证据不足不能被强制解释为正常 | `frame_findings`，含时间偏移、视觉状态、置信度、证据文本、原始响应 |
| 事件候选/事件 | 服务端按规则把观察跨时间聚合后形成的一次业务异常 | 零事件也是分析结果；多个命中帧不应变成多个重复事件 | 聚合器和 `inspection_events`；事件关联 `run_id`、规则、严重度、状态 |
| 事件证据 | 说明首次发现、确认、峰值或恢复的画面/时间点 | 证据是判定依据，不是整改完成证明；误报后也须保留 | `event_evidence`，关联 `frame_findings` |
| 严重度 | 异常本身的业务风险与处置优先级，如 P0/P1/P2 | **不代表**规则成熟度、模型置信度或是否允许自动通知 | 事件创建时固化 `severity`；历史事件不随新配置回写 |
| 规则能力状态 | 代码可运行、合成样本已回归、真实门店已验收等证据层级 | 与事件严重度正交；“已解决事件”不等于“规则正式验收” | 目前主要由前端规则台账和审计文档说明 |
| 人工决定 | 确认、误报、指派、开始整改、解决等有操作者的状态变化 | AI 恢复画面不自动等于人工验收通过 | `event_action_logs` 和事件时间线 |
| 通知 | 基于已形成事件的对外发送尝试及结果 | 告警针对事件，不针对工单；发送失败不改写分析成功 | `notification_deliveries`；本轮视频样本验收不以飞书为条件 |

### 2.1 ID 与溯源约束

一条可追查链路应保留 `video_id → run_id → finding_id → event_id → action_log_id`。事件详情至少能反查任务、规则编码、视频来源和关键证据；分析任务也能跳转到所形成事件。没有事件时保留任务、模式、粗筛结果及零事件结论。时间需区分视频中的 `captured_offset`、任务处理时间和人工操作时间，不用墙上时钟代替视频时间。

**拟补而非现有事实**：为今后的重放比较，在每次运行/事件中保存规则配置版本、Prompt 版本、模型版本或可复核指纹；现有表记录 `model_id`，但未见独立的规则版本和 Prompt 版本字段。补齐前不能宣称历史结果可按完整同版本条件复现。

## 3. 规则和建议（策略层）

策略层接收可见事实和业务配置，给出“是否形成事件、事件等级、是否需要人工复核、建议处置”；它不把模型自由文本当业务制度。

| 规则 | 已确认的业务等级 | 当前聚合口径 | 当前证据/运行边界 | 当前通知边界 |
| --- | --- | --- | --- | --- |
| E1 冰箱门持续开启 | P0；旧 P1 事件保留原值 | 连续开启达 30 秒；短开不成事件；关门恢复单独记录 | 3 条合成视频样本级回归，非实时萤石监控 | 测试群通知可选；P0 响应时限和自动升级未验收 |
| B1 疑似烟雾/异常明火 | P0；旧 P2 事件保留原值 | 双层粗筛/关键帧复核，疑似烟雾/明火持续约 2 秒；蒸汽不应触发 | 3 条合成视频样本级回归；首轮漏检保留为风险；仍须人工复核 | 自动通知关闭，可对合格事件显式发测试卡片 |
| A1 未佩戴口罩或一次性手套 | 页面/代码现值 P2，业务等级尚待逐条确认 | ROI、多帧命中；模型观察与后端聚合分离 | 2 条合成视频正负样本级回归；单项缺失、遮挡、多人未覆盖 | 不自动通知 |

以上是**当前实现与已确认口径的并列记录**，不是把样本级回归写成真实门店验收。A2/C1/A3/A4 仍是上传可选、缺真实模型视频实测；G1 等仍为研究候选。旧技术设计中 E1=P1、B1 首帧强告警等描述是早期目标，不覆盖本表的当前运行事实。

策略决策的最小输出建议为：`run_id`、`rule_code`、`candidate_interval`、`decision`（形成事件/未形成/证据不足）、`reason_code`、`evidence_finding_ids`、`rule_config_version`、`severity_at_creation`、`human_review_required`、`notification_policy`。这是**拟定契约**，不是当前 API 响应。对零事件也应给出可审计的原因类别，例如“无候选段”“候选未达时长”“证据不足”，而不是仅显示 0 条。

### 3.1 决策权边界

- 模型：只判断可见状态、置信度、证据及不足以判断；不能自由设定 P 等级、SLA、负责人或处分。
- 服务端规则：负责时长、多帧门槛、去重、事件等级、通知开关和建议模板；版本变更不得静默改写旧事件。
- 人工：确认或否定事件，指派和记录整改依据；不得通过“已解决”反推模型正确。
- P0 是风险等级，不是“验证成功等级”；P0 也不自动授权飞书发送或 SLA 升级。E1/B1 的 P0 计时起点及响应目标尚须业务确认。

## 4. 执行和反馈（行动层）

现有流程为 `pending_confirmation → acknowledged → rectifying → resolved`，另有 `false_positive`/`ignored` 分支；指派和状态操作写入时间线。整改工单页目前主要是事件投影，不应在文档中称为独立审批/工单引擎。

| 阶段 | 当前页面/操作 | 后续需要说清的判定口径 |
| --- | --- | --- |
| 分析结束 | 任务列表和详情展示结论、事件数、耗时、Token、估算模型费用 | “任务成功”“发现候选”“形成事件”分别显示；零事件和失败可追溯 |
| 事件待确认 | 事件详情显示证据帧、时间轴、等级、状态、确认/误报按钮 | 人工确认是业务接受，不是改变原始模型观察；误报原因保留 |
| 整改执行 | 指派负责人、开始整改、填写处理结果 | 负责人、动作、时间和说明必须可追溯；AI 恢复画面不自动关闭 |
| 复核/关闭 | 当前有“提交整改结果/确认已解决”和时间线 | 独立复核人、复核证据、重开条件尚未形成完整制度；不得宣称已有双人复核 |
| 对外通知 | 飞书卡片测试发送、投递记录 | 以事件为发送单位；本轮视频验收排除飞书送达，生产自动通知另行验收 |

行动反馈未来应反哺**规则评估**：误报、漏报、人工驳回原因与真实整改结果作为样本审计，不自动修改阈值或让模型自我批准上线。没有真实门店授权样本前，只能报告合成样本级表现。

## 5. 对现有页面的差距核查

| 页面 | 已有，不重做 | 拟补/待核实 | 优先级 |
| --- | --- | --- | --- |
| 分析任务 | 状态、进度、规则、模式、事件数、耗时、调用/Token、费用估算；可进任务详情和事件 | 结构化记录零事件原因；把候选段、规则门槛和最终结论放在同一条可追查链路 | 先做数据核查，再决定 UI |
| 事件详情 | 视频/证据帧、异常时间轴、P 等级、负责人、SLA 字段、人工时间线 | 显示规则/Prompt/模型版本（先保证采集，不能仅前端补文案）；明确“模型观察/规则判定/人工决定”三段 | 数据契约优先 |
| 规则能力 | 每条规则的当前策略、样本证据、等级和实时接入边界 | 前端 `ruleCatalog.js` 为手写台账，后端规则是运行权威；需要防止两处漂移。A1/A2/C1/A3/A4 业务等级待确认 | 高 |
| 整改跟踪/工单 | 筛选、状态、指派、说明与处理时间线 | 独立复核门槛、重开条件和前后证据要求尚未定义；先定业务，再考虑按钮 | 待业务决定 |
| 线上演示 | Pages + D1 可保存演示状态，免密码选择演示角色 | 不是真实鉴权；云端不运行上传/AI/实时流/飞书；不可拿演示操作当本地真实分析证据 | 保持边界 |

**本轮文档工作不修改页面、数据库、线上数据或规则。** 下一轮若实施，应先核查每个待补项的 API/数据库事实，再只修改确有缺口的位置；不新增“三层决策”导航页。

## 6. 最小落地顺序与验收

1. **统一口径**：以本表为讨论底稿，请业务确认 A1 等未定等级、P0 计时与人工复核定义。同步修订早期文档冲突，保留历史记录和创建时等级。
2. **先补可追溯数据，不重排页面**：为新任务固化模型、Prompt、规则配置版本及来源标签；为零事件记录结构化原因。旧任务字段缺失应显示“当时未记录”，不得补造版本。
3. **复用现有页面呈现**：仅在任务详情和事件详情增加必要的判定链路；规则页从同一可信配置/版本读取或建立自动一致性校验，避免前后端两套结论。
4. **固定样本回归**：先以既有 E1/A1/B1 的 8 条可复核合成视频验证正例、负例、零事件、恢复、误报、人工操作和历史等级不回写。模型/Prompt/规则变更后重复测试。飞书、实时萤石和真实门店准确率不作为这一轮通过条件。

验收时至少能从某个事件回到**来源任务、视频来源、关键帧、规则条件、创建时等级、人工决定及处理结果**；零事件任务同样能说明为什么没有事件。若某项仅有文案而没有保存的依据，不算通过。

## 7. 跨 MVP 可复用与不可复用的部分

可复用的是对象关系和责任边界：`可核查事实 → 版本化规则/指标 → 建议行动 → 授权人决定 → 执行记录 → 效果反馈`。例如加盟商运营系统中的库存/调拨决策也可保留事实口径、审批人与执行结果。但库存数量、铺货率、区域调拨规则与视觉巡检的帧观察、异常严重度并非同一语义，不能强行共用一个事件表或 P 等级。当前巡店系统与加盟商运营系统**没有跨系统同步**；若将来互通，先约定稳定门店编码、数据权限、幂等接口和审计归属，再考虑自动执行。
