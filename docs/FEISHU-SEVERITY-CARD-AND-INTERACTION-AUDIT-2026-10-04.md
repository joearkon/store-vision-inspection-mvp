# 飞书 P0/P1/P2 卡片联调与卡内裁决方案（2026-10-04）

## 本次结论

向已配置的“小茶日记”群自定义机器人 Webhook **各发送一张明确标注“测试·合成视频”的 P0、P1、P2 版式卡**。三次 HTTP 均为 200，飞书业务 `code=0`。这证明当前群 Webhook 接收了三种颜色/文案的交互式卡片请求；**尚无飞书客户端截图复核**，不能据此宣称显示细节、按钮点击或卡内裁决已验收。

| 卡片 | 数据依据 | 本次测试性质 | 接口结果 |
| --- | --- | --- | --- |
| P0 | 当前本地库没有新 P0 事件 | B1 风险等级的**纯模板**，卡面明示“无事件编号、无模型判定、非现场告警”；未伪造安全事件 | HTTP 200 / `code=0` |
| P1 | 历史 E1/P1 事件 `EVT-0929-81F53E` | 展示事件创建时等级；同时注明 E1 当前新事件为 P0，历史等级不回写 | HTTP 200 / `code=0` |
| P2 | 历史 A1/P2 事件 `EVT-0929-8CB4E8` | 展示创建时代码等级；同时注明 A1 最终业务等级待确认 | HTTP 200 / `code=0` |

三张仅作**版式与分级联调**：没有裁决按钮、没有可误点的详情链接，没有调用本地 `/api/feishu/test-send`，没有写入 `notification_deliveries`、事件或工单，也没有启用自动告警。P1/P2 引用的历史事件已经“已解决”；不是新产生的告警。发送密钥仅从本地 `.env` 读取，未写入卡片或文档。群机器人 Webhook/加签密钥此前曾出现在聊天中，正式使用前仍应轮换。

## 当前系统与飞书能力边界

- 项目现有真实事件发送接口只允许 E1/P0、E1/P1，以及**人工显式测试**的 B1/P0；历史 B1/P2 与 A1/P2 不可从该接口误发为当前 P0 告警。网页卡片页目前只有 P0、历史 P1、SLA 示意三个标签，**尚无 P2 正式发送入口**。本次 P2 是一次性版式测试，不意味着通知策略已经开放。
- 当前投递优先走**群自定义机器人 Webhook**。卡片中的“查看详情”属于 URL 跳转；“标记已处理”在页面上是禁用的原型控件。已有应用机器人尝试曾因机器人不在目标群而被飞书拒绝；本次没有验证应用机器人送达。
- [飞书官方《发送卡片》](https://open.larkenterprise.com/document/feishu-cards/send-feishu-card)将自定义机器人 Webhook 归于未配置请求回调交互的一次性群卡片；通过应用调用接口发送的卡片才支持请求回调交互和操作后更新。因此不能在现有 Webhook 上仅加一个按钮，就把点击安全地写回巡店事件。
- [飞书官方卡片回传交互回调](https://open.feishu.cn/document/feishu-cards/card-callback-communication)对应 `card.action.trigger`。它提供卡片动作与操作者信息，由应用配置的回调服务接收；是否可用仍需在本项目完成应用机器人入群、配置、验签、权限与端到端联调。

## 如果要在飞书卡片内直接裁决

建议分两步，而不是把“收到通知”和“判定属实”混成一个按钮。

### 1. 最小安全交互

卡片保留“查看证据/详情”URL。企业应用机器人送卡并接收回调后，先只开放**确认收到/正在核查**：记录飞书操作者和时间，但不改变视觉判断、不直接标记已解决。P0 还应保留未响应计时和人工电话/现场流程的业务预案；本项目尚未定义和验收 P0 SLA，不能在卡片上显示虚构倒计时。

### 2. 真正裁决与整改

仅在证据可访问、身份可校验的前提下，考虑以下动作：

| 当前状态 | 卡片动作 | 服务端要求 | 结果 |
| --- | --- | --- | --- |
| 待人工确认 | 确认属实 | 回调验签；飞书用户映射到真实巡检账号；校验门店权限和事件最新状态 | 写入 `event_action_logs`，转为已确认 |
| 待人工确认 | 判为误报 | 同上，且要求误报原因；P0 建议额外复核，不做单击静默撤销 | 保留原始证据，转为误报 |
| 已确认 | 指派整改 | 校验负责人属于可授权范围，并要求处理说明 | 记录负责人和操作日志 |
| 整改中 | 提交整改/复核 | 要求整改结果及可核查证据；复核人/重开规则须先由业务定义 | 不能让一个按钮无证据地直接“已解决” |

每次回调应携带事件 ID、预期状态/版本、动作和一次性请求标识；服务端验证来源与回调签名、操作者身份、租户/门店权限、事件是否仍在可操作状态，再用幂等事务更新事件与审计日志。重复点击或旧卡片点击应返回“状态已变化”而非重复执行。成功后更新卡片状态或显示明确反馈；发送/回调失败不能改写成功的分析任务。**群里的卡片展示不是授权凭据**，不能信任卡片里传来的等级、负责人或规则文字。

## 为什么现在不能直接上线卡内裁决

1. 当前群 Webhook 卡片没有请求回调能力；需要改为企业应用发卡，并完成应用入群及回调配置。
2. 线上 Pages 演示为免密码角色选择，公开访客能选择管理员；它只适合合成数据演示，不能用作飞书回调的真实身份和权限基础。
3. 云端当前没有视频解析/原视频访问，详情证据主要是静帧快照；“确认属实/误报”前需确认复核者能看到足够证据。
4. P0 SLA、复核角色、误报撤销和整改完成证据的业务规则仍待明确；不能用卡片按钮抢先定义业务制度。
5. 本次只拿到飞书接口接收结果，客户端显示、移动端点击、回调、重复点击、越权和卡片更新都未测试。

## 推荐下一轮验收顺序

1. 用户在测试群核对这三张卡的客户端实际显示；记录截图中的标题、颜色、换行和风险提示，不把 API 接收等同于视觉通过。
2. 明确 P2 是否只进系统、是否允许人工发测试卡；确认 A1 等规则的最终业务等级。P0/P1/P2 是风险等级，不是规则成熟度。
3. 若要卡内裁决，先让**企业应用机器人**进入测试群，配置最小权限和卡片回调；用一条专门测试事件验证“确认收到”及审计，不先开放“已处理”。
4. 再用真实登录、飞书用户映射和门店权限测试“确认属实/误报/指派”，覆盖重复点击、过期卡片、无权限和证据不足。通过后才考虑正式通知策略。

- 实现范围：本次没有改应用代码、页面、数据库或线上部署；只做三张一次性群卡片版式联调与本说明文档。
- 自动化依据：既有 `tests/test_feishu_card_api.py`、`tests/test_notifier.py` 覆盖当前真实事件的预览、允许等级、Webhook 签名、发送幂等和拒绝误级；它们不覆盖本次一次性 P2 版式或未来回调。
- 产品逻辑：模板 P0 与真实事件严格区分；P1/P2 仅引用历史记录的创建时等级；外发不生成工单或变更整改状态。
- 视觉比较：尚未获取客户端截图，故**未通过飞书视觉验收**；页面原型不因本次测试改变。
