# UI v2 与人工整改闭环：交付审计

日期：2026-09-28。视觉参考：`references/original-v2/`（用户提供的 `门店视觉巡检 Demo (2).zip`）。参考代码中的 `WORK_ORDERS`、多门店 `STORES`、自动派单和电话升级均为原型演示数据，不进入真实业务管线。

## 已交付

- 新导航和页面：门店总览、整改工单。总览按当前真实单店、摄像头和事件展示 5 个指标、门店状态、异常类型、最新告警；SLA 达标率口径未定时显示 `—`，不虚构评分。
- 工单页还原四指标、状态筛选、左侧列表/右侧详情、关联事件、处理时间线与人工指派入口。当前以事件为工单载体，不另建假工单 ID。
- 事件详情新增指派/更换负责人、误报原因、整改结果说明；后端校验状态迁移、门店范围内有效账号，动作和说明写入时间线。
- 整改跟踪列表新增状态/严重度/时间筛选、搜索、导出和分页；CSV 防公式注入。
- 上传页取消规则必选；按摄像头区域自动选择**已实现的** E1 或 A1。未实现的后厨/取餐规则明确禁止提交，避免把别的规则冒充检测。
- 规则能力页纳入 v1.1 的 G1、A6、F1/F2、F3/F4 等编号与名称，明确区分「可运行」和「待开发/待验证」；新增项不参与分析任务。
- 修正大盘「今日异常」之前只数最近 8 条的错误：现在按门店时区的当日事件统计，待处理数按全量事件统计。

## 测试证据

- Python 3.10：`python -m unittest discover -s tests -q`，31 个测试通过。默认 Conda Python 未安装 FastAPI，故需用项目已安装依赖的 Python 3.10 运行。
- Web：`npm test -- --run`，13 个测试通过（含工单筛选与单店状态投影）；`npm run build` 通过。
- 本地浏览器：`#/stores` 显示当前单店真实数据，「今日异常」在 API 重启后由错误的 7 更正为 1；`#/workorder` 显示真实 7 条事件及相应时间线，没有加载假原型工单。

## 仍需产品/工程确认

- 当前组织初始化只有「总部巡检管理员」一个可指派账号，缺门店店长/区域主管账号；因此可以验证人工指派流程，但不能演示真实跨角色分派。
- 旧事件可能在新流程上线前已解决却没有负责人；页面忠实显示「尚未指派」，不追填伪记录。
- 自动派单、SLA 逐级升级、短信/电话通知、多门店健康分均未实现；用户本轮确认先做页面和人工指派闭环。
- 当前工作单由事件直接映射，`/api/events` 默认只返回最近 50 条；多门店/大批量分页与独立工单实体尚未实现。
- HTTP API 仍是本地测试站点的单管理员模式，尚未接入真正的登录鉴权；操作日志中的 `actor_id` 不能视为可信身份凭证。
- 用户重新上传的 v1.1 已修正 A1/F1/F2 编码冲突，详见 `RULE-PACK-V1.1-INTAKE-REVIEW-2026-09-28.md`；新增规则仍未激活。
- 视觉核对覆盖新版页面布局与主交互；尚未完成逐像素截图比对或移动端适配，桌面站点仍按原型的固定宽布局。
