# 门店 AI 视频巡检 MVP 场景与技术实现设计

> 文档状态：v1.0（实现基线）  
> 更新日期：2026-09-27  
> 适用阶段：单门店真实链路 MVP  
> 原型作用：视觉与交互参考；当原型与本文冲突时，以本文的业务状态、规则边界和技术约束为准。

## 1. MVP 要回答的问题

本阶段不追求“识别尽可能多的异常”，而是验证下面五件事是否真实成立：

1. 普通门店视频能否形成稳定、可解释的异常判断。
2. 系统能否理解持续时间，而不是只分析孤立截图。
3. 同一异常能否合并成一个事件，避免告警流水爆炸。
4. 总部或店长能否从飞书进入事件详情并完成整改闭环。
5. 每一次模型判断、状态变化和人工操作能否追溯。

成功标准不是模型给出漂亮文字，而是产生“有视频证据、可人工确认、可闭环”的巡检事件。

## 2. MVP 边界

### 2.1 本期包含

- 独立的组织、区域、门店、账号、角色和数据范围初始化。
- 本地 MP4 上传分析。
- 预置演示视频分析；上传和预置视频共用同一条真实分析管线。
- FFmpeg 抽帧和视频元数据读取。
- 豆包 Vision 结构化视觉判断。
- 按规则配置的多帧聚合、持续时间判断、事件合并和解除。
- Dashboard、分析任务、事件列表、事件详情和证据时间线。
- 人工确认、误报标记、整改中、已解决。
- P0/P1 飞书告警；飞书详情链接跳转回 SaaS。
- 分析任务、模型调用、事件、通知和人工操作审计日志。

### 2.2 本期不包含

- 与加盟商订货、盘点、库存或经营助手同步。
- 生产级 RTSP 长连接和大规模摄像头并发。
- 自动处罚、自动扣分或无人工确认的责任认定。
- 短信、电话告警。
- 独立的复杂工单系统和跨组织审批流。
- 仅凭普通监控画面对配方重量、保质期、证件有效期或通道厘米数作确定判断。

## 3. 英雄场景

MVP 以四个英雄场景验收。它们分别验证时序理解、区域规则、环境识别、高危快速告警和整改闭环。

### 3.1 S1 冰箱门持续开启

**业务价值**：降低冷链风险和原料损耗。  
**能力重点**：状态持续时间、多帧合并、恢复检测。

流程：

```text
冰箱门打开
→ 记录观察状态，不立即告警
→ 持续达到 30 秒
→ 生成 E1 已确认事件
→ 保存开始帧、确认帧和过程证据
→ Dashboard 高亮并发送飞书 P1
→ 冰箱门关闭
→ 记录“异常已消失”，等待人工确认整改结果
```

验收要求：

- 短暂开门不产生正式事件。
- 同一次持续开启只生成一个事件。
- 事件展示首次发现时间、确认时间、累计持续时间和恢复时间。
- 视频循环重放不得重复发送同一轮演示告警。

### 3.2 S2 操作区着装不合规

**业务价值**：稳定执行门店卫生规范。  
**能力重点**：人员、着装、区域 ROI 和连续帧确认。

第一版正式支持：

- A2 未戴工作帽或发网。
- C1 未穿工作围裙或指定工服。

判断必须同时满足：

1. 人员进入已配置的制作区 ROI。
2. 人员可见度达到最低要求。
3. 连续多个有效观察帧均命中。

“未佩戴手套”保留为实验规则，不作为第一版验收主项。普通远距离监控中手部像素、遮挡和动作变化会显著影响准确率。

### 3.3 S3 地面积水或操作台脏乱

**业务价值**：降低滑倒和食品卫生风险。  
**能力重点**：环境状态、持续观察、整改前后证据。

流程：

```text
发现疑似积水/明显污渍
→ 连续存在达到规则阈值
→ 生成 A3/A4 事件
→ 负责人确认并开始整改
→ 员工完成清洁
→ 摄像头自动观察恢复，或人工上传整改照片
→ 整改前后证据并排展示
→ 人工关闭事件
```

系统不得因为单帧反光或阴影直接生成确认事件。环境类异常默认需要更长的观察窗口。

### 3.4 S4 明显烟雾或异常明火

**业务价值**：验证高危场景的快速发现与升级能力。  
**能力重点**：P0 快速预警、后续确认、SLA 与误报处理。

流程：

```text
首帧发现高置信度烟雾/异常明火
→ 立即生成 P0 预警
→ 后续有效帧继续命中
→ 升级为 P0 已确认事件
→ 飞书强告警
→ 未确认时按 SLA 升级
→ 异常消失后保留完整证据，等待人工关闭
```

P0 不机械等待统一三帧后才通知。首帧可以预警，连续证据用于确认或撤销。

## 4. 规则分层与首期规则集

### 4.1 正式验收规则

| 编码 | 规则 | 能力类型 | 默认严重度 | 默认确认策略 |
|---|---|---|---|---|
| E1 | 冰箱门持续开启 | 多帧时序 | P1 | 持续 30 秒 |
| A2 | 操作区未戴工作帽/发网 | ROI + 多帧 | P1 | 最近 5 个有效帧命中至少 3 帧 |
| C1 | 操作区未穿围裙/工服 | ROI + 多帧 | P1 | 最近 5 个有效帧命中至少 3 帧 |
| A3 | 操作台明显脏乱 | 环境 + 多帧 | P1 | 持续 60 秒或人工确认 |
| A4 | 地面积水/明显垃圾 | 环境 + 多帧 | P1/P2 | 最近 5 个有效帧命中至少 3 帧 |
| B1 | 明显烟雾/异常明火 | 高危快速检测 | P0 | 高置信度首帧预警，后续 2 帧确认 |

严重度由后端规则配置映射，模型不得自行决定最终严重度。

### 4.2 实验规则

- A1 未佩戴手套。
- F1 取餐区堆积混乱。
- F2 顾客排队拥挤。

实验规则可以保存观察结果，但默认不触发真实飞书告警，也不纳入 MVP 准确率承诺。

### 4.3 暂不支持的确定性判断

- D1 配方用量错误：需要配方数据、量具或动作序列。
- D3 原料过期：需要清晰标签 OCR 和批次数据。
- C2 健康证过期：需要固定公示区域、OCR 和证件日期解析。
- B3 通道宽度小于 1.2 米：需要摄像头空间标定。
- 燃气阀门内部状态、电器真实过载：需要专用传感器或近距离证据。

## 5. 演示视频与验收素材

AI 生成视频用于展示流程和压力测试，不作为模型真实准确率的唯一证据。

建议准备：

1. 一段 3–5 分钟连续故事视频：正常营业、着装异常、冰箱超时、地面泼洒、清洁恢复。
2. 一段 20–40 秒 P0 烟雾或异常明火视频。
3. 每个正式规则至少一段正常负样本，防止只测试“必然有异常”的视频。
4. 后续补充经过授权的真实监控样本或受控实拍样本，用于评估真实摄像头画质、角度和遮挡。

预置视频每次运行都必须生成新的 `analysis_run_id`，但演示循环默认关闭外部通知；只有用户明确点击“发送演示告警”时才推送飞书。

## 6. 业务对象与状态模型

### 6.1 核心对象

```text
Organization
└─ Region
   └─ Store
      └─ CameraSource

VideoAsset
└─ AnalysisRun
   ├─ Frame
   │  └─ FrameFinding
   └─ InspectionEvent
      ├─ EventEvidence
      ├─ EventActionLog
      └─ NotificationDelivery
```

- `VideoAsset`：上传视频或预置视频。
- `AnalysisRun`：一次可重试、可追踪的分析任务。
- `FrameFinding`：模型对某一帧的原始观察，不等同于业务事件。
- `InspectionEvent`：多帧聚合后的业务事件。
- `EventEvidence`：开始、确认、峰值、恢复、整改后的证据。
- `EventActionLog`：确认、指派、备注、误报、整改、关闭等审计记录。
- `NotificationDelivery`：每次飞书发送、失败、重试和消息标识。

### 6.2 事件状态

```text
observing（观察中，不进入业务列表）
→ pending_confirmation（待人工确认）
→ acknowledged（已确认）
→ rectifying（整改中）
→ resolved（已解决）

分支：false_positive（误报） / ignored（已忽略）
```

`overdue` 不是独立状态。系统根据 `due_at`、当前时间和是否为终态动态计算超时标记。

### 6.3 事件合并键

基础事件键：

```text
store_id + camera_id + rule_code + roi_id + subject_track_id(optional)
```

只要同一事件仍在活动窗口内，新命中就更新 `last_seen_at`、持续时间、最高置信度和证据，不新建事件。异常消失超过规则配置的关闭间隔后，才允许下一次同类异常创建新事件。

## 7. 技术架构

```text
Web 前端
  ├─ 上传 MP4
  ├─ 启动预置视频分析
  └─ 查询任务、事件和整改状态
          ↓
FastAPI
  ├─ 身份与权限
  ├─ 视频与分析任务 API
  ├─ 事件与整改 API
  └─ 飞书跳转/回调 API
          ↓
SQLite 持久化任务队列
          ↓
Worker
  ├─ ffprobe 获取元数据
  ├─ ffmpeg 抽帧
  ├─ 画质/变化过滤
  ├─ 豆包 Vision 调用
  ├─ JSON Schema 校验
  └─ 规则聚合与事件写入
          ↓
本地文件存储（MVP） + SQLite
          ↓
通知 Worker → 飞书机器人
```

约束：

- 不使用内存任务或普通 `BackgroundTasks` 承担长视频分析。
- 任务状态必须持久化，服务重启后可以恢复或安全重试。
- 本地文件系统仅用于单机 MVP；云部署时迁移至对象存储。
- 密钥只从环境变量或密钥服务读取，不写入数据库、日志或仓库。

## 8. 视频处理策略

### 8.1 基础抽帧

- 默认基础频率：1 fps。
- 读取原视频时间戳，不以处理时间代替事件时间。
- 对相邻帧做变化检测；几乎无变化的帧可跳过大模型调用。
- P0 关注区域可配置更高采样率，但必须有调用上限。
- 保留用于事件证据的原始帧；非事件帧按保留策略清理。

### 8.2 画质门槛

进入规则判断前检测：

- 图像是否过暗或过曝。
- 目标区域是否被严重遮挡。
- 人体/设备是否达到最低像素尺寸。
- 摄像头是否移动或画面是否失焦。

证据不足时返回 `insufficient_evidence`，不能强制输出正常或异常。

## 9. 模型输入输出契约

### 9.1 模型职责

模型负责：

- 描述可见事实。
- 返回候选规则编码和视觉置信度。
- 指出证据位置和可见度。
- 明确表达证据不足。

后端负责：

- 规则启用范围。
- 最终严重度和 SLA。
- 制度条款与整改建议模板。
- 多帧确认、事件合并、通知和状态变化。

### 9.2 建议输出结构

```json
{
  "frame_id": "uuid",
  "camera_id": "CAM-001",
  "captured_at": "2026-09-27T09:23:07+08:00",
  "image_quality": "usable",
  "observations": [
    {
      "rule_code": "A2",
      "visual_state": "violation",
      "confidence": 0.91,
      "evidence": "制作区内员工头发裸露，未见工作帽或发网",
      "bbox": [0.31, 0.18, 0.52, 0.83],
      "visibility": "clear"
    }
  ]
}
```

要求：

- 使用服务端支持的结构化输出或 JSON Schema。
- Schema 校验失败时保留原始响应并有限次数重试。
- 不以正则提取作为正常解析路径。
- 模型响应中的严重度、制度条文和自由生成建议不得直接作为业务真值。

## 10. 飞书告警设计

### 10.1 告警规则

- P0：首帧高置信度预警，确认后更新同一事件；未响应按 SLA 升级。
- P1：事件确认后发送一次。
- P2 和实验规则：默认只进入 Dashboard。
- 同一事件更新不重复创建新告警；优先更新原卡片或发送受控升级消息。

### 10.2 卡片动作

- `查看详情`：使用带事件 ID 的 SaaS URL。
- `确认收到`：只有当前飞书机器人具备卡片动作回调能力时启用。
- `标记已处理`：必须经过权限检查，且不能直接跳过整改证据和审计日志。

如果当前机器人只是群自定义 webhook，则 MVP 首期仅启用 URL 跳转；状态操作在 SaaS 内完成。若为应用机器人，则实现回调验签、用户绑定、权限校验和幂等处理。

所有发送请求使用 `notification_key` 保证幂等：

```text
event_id + notification_type + escalation_level
```

## 11. 组织和权限初始化

首期角色：

| 角色 | 数据范围 | 主要权限 |
|---|---|---|
| 系统管理员 | 全组织 | 初始化、账号、规则和系统配置 |
| 总部巡检 | 全部门店 | 查看事件、确认、指派、关闭、导出 |
| 区域负责人 | 所属区域 | 查看和跟踪区域事件 |
| 店长 | 所属门店 | 确认、整改、上传证据、关闭申请 |
| 查看者 | 授权门店 | 只读查看 |

账号、角色、门店范围和飞书用户映射均由本系统独立维护。首期通过 seed 数据初始化，不依赖现有加盟商系统。

## 12. 可追溯性与数据保留

必须记录：

- 视频来源、文件哈希、上传者和上传时间。
- 抽帧参数、模型名称、模型版本和 Prompt 版本。
- 每次模型请求的状态、耗时、重试次数和 token/费用信息。
- 从帧观察到事件的聚合依据。
- 每次人工确认、误报、整改、关闭和通知操作。

默认建议：

- 原始演示视频：保留 30 天，可配置。
- 非事件帧：分析完成后 24 小时内清理。
- 事件证据帧：保留 180 天，可配置。
- 审计记录：长期保留，不随视频删除而消失。

正式上线前需按所在国家和组织政策确认视频隐私、员工告知、访问控制和最终保留期限。

## 13. MVP 验收标准

### 13.1 功能验收

- 上传合法 MP4 后可以看到真实任务进度和失败原因。
- 服务重启后，未完成任务不会无记录地消失。
- 四个英雄场景均能产生对应的可解释结果。
- 同一持续异常不会生成大量重复事件。
- 事件详情具有开始、确认、峰值、恢复或整改证据。
- 人工可标记误报，且误报不会被删除。
- P0/P1 告警可追踪发送结果，重复执行不会重复轰炸群聊。
- 不同角色只能查看和操作授权范围内的数据。

### 13.2 质量验收

- 每个正式规则至少有正样本和负样本。
- 测试结果可按同一视频、同一模型和同一 Prompt 版本重放。
- 不使用随机置信度作为真实验收结果。
- 模型证据不足时能够返回“不足以判断”。
- AI 生成视频的效果与真实/受控实拍样本的效果分开统计。

### 13.3 视觉验收

- 现有原型作为桌面端视觉基线。
- Dashboard、事件详情、上传分析、整改状态和飞书卡片需逐页截图对照。
- 正常、加载、空数据、失败、无权限和超时状态均需有明确页面表现。
- 生产实现不得依赖浏览器运行时 Babel 或原型 CDN 脚本。

## 14. 推荐实施顺序

1. 数据模型、组织权限、规则配置和状态机。
2. 视频上传、文件存储、持久化任务队列和 Worker。
3. FFmpeg 抽帧、画质过滤和任务进度。
4. 豆包 Vision 结构化输出及调用审计。
5. E1、A2、C1 三条规则聚合。
6. A3、A4、B1 和恢复检测。
7. Dashboard、事件详情和整改闭环。
8. 飞书通知、幂等和可选回调。
9. 正负样本测试、视觉对照和部署验证。

## 15. 开工前仍需确认

- 当前飞书机器人是群自定义 webhook，还是具备卡片回调的应用机器人。
- 单个上传视频允许的最大时长和文件大小。
- MVP 部署在本地演示机、云服务器还是现有 Cloudflare 架构旁路。
- 事件证据和原视频最终保留期限。
- 第一批真实或受控实拍样本的取得方式。
